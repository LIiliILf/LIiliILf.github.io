RAG 实践笔记

main.py 先会调用大模型
→ simple_rag_v1.py 再做一个关键词版 RAG
→ embedding.py 理解 embedding
→ fetch_model.py + file_db.py 再用 Chroma 做向量检索
→ simple_rag_v2.py 再把向量检索接入 RAG
→ simple_rag_v3.py 最后用 LangChain 重写一版

1. main.py：先确认大模型 API 能调用

这一部分测试 DeepSeek API。

代码做了三件事：

流程是：读取 DeepSeek API Key → 创建 OpenAI 兼容客户端 → 向 deepseek-chat 发送问题 → 打印模型回答

因为 DeepSeek 的接口兼容 OpenAI SDK，所以用的是：from openai import OpenAI

但实际请求地址是：base_url='https://api.deepseek.com'

这一节打通：Python → DeepSeek 大模型

2. simple_rag_v1.py：关键词匹配版 RAG

这是第一版 RAG 。流程如下：

用户问题 → 根据文件名做关键词匹配 → 读取命中的 txt 文件内容 → 把内容放进 prompt → 交给 DeepSeek 回答

核心函数有三个：

对应 RAG 三步：

函数 作用 对应 RAG 环节
retrieval() 从本地知识库找资料 检索
augmented() 把资料和问题拼成 prompt 增强
generation() 调用大模型生成答案 生成

retrieval() 做了什么？

这里的逻辑是：遍历 my_knowledge 里的所有 txt 文件 → 看文件名是否出现在用户问题里 → 如果出现，就读取这个文件内容 → 拼到 context 里

比如知识库里有文件：探索者X100型无人机.txt

用户问：探索者X100型无人机有多少种飞行模式？

因为问题里包含文件名 探索者X100型无人机，所以会命中这个文件。

这个版本的检索比较简单，其实是文件名关键词匹配，而不是语义检索。

augmented() 做了什么？

如果没有检索到 context：return f'请简要回答下面问题: {query}'

如果检索到了 context：

这一步就是 RAG 里的 Augmented：原始问题 → 加上检索到的资料 → 变成增强后的 prompt

也就是让模型不要凭空回答，而是基于上下文回答。

generation() 做了什么？

它就是调用 DeepSeek：

最后返回：completion.choices[0].message.content

所以 simple_rag_v1.py 的完整链路是：

query → retrieval(query) → context → augmented(query, context) → prompt → generation(prompt) → answer

这个版本适合理解 RAG 的基本思想，但局限很明显： 它只能匹配文件名，不能理解语义。

5. file_db.py：把本地 txt 文件存入 Chroma 向量数据库

它做的是：读取 my_knowledge 里的 txt 文件 → 用 BGE 模型转成 embedding → 存入 ChromaDB

第一步：加载 embedding 模型

model = SentenceTransformer(r'model_dir\BAAI\bge-large-zh-v1___5')

这里加载的是刚才下载好的本地模型。

注意： v1___5 是 ModelScope 下载后的本地目录命名方式，原模型名里的 . 被替换成了 ___。

第二步：创建 Chroma 持久化数据库

client = chromadb.PersistentClient('./chroma_v2')

类型 特点
EphemeralClient() 内存数据库，程序结束数据消失
PersistentClient() 持久化数据库，数据保存到本地

第三步：创建 collection

collection 可以理解成向量数据库里的一张表。

这里创建了一个叫：da_fei 的 collection。

hnsw:space = cosine 表示用 cosine 距离做相似度检索。

第四步：读取知识库文件

path_list = list(Path('my_knowledge').glob('*.txt'))意思是：找到 my_knowledge 文件夹下所有 txt 文件

然后：把每个 txt 文件的完整内容加入 text_list。

这里要注意：这里不是按段落切 chunk，而是一个 txt 文件作为一个 document。

所以它的单位是：文件级 document

不是更细的：段落级 chunk

第五步：生成 embedding

embeddings = model.encode(text_list)

假设有 10 个 txt 文件，每个 embedding 是 1024 维，那么结果大概是：(10, 1024)也就是：10 个文本文件转成了 10 个向量。

第六步：写入 ChromaDB

这里写入了四类信息：

字段 含义
embeddings 文本对应的向量
documents 原始文本内容
metadatas 元数据
ids 每条数据的唯一 ID

这一节结束后，知识库就存入了向量数据库：

my_knowledge/*.txt → text_list → embeddings → ChromaDB / chroma_v2

7. simple_rag_v2.py：向量检索版 RAG

这一版是把 file_db.py 里的向量检索接入到 RAG 生成流程，形成一个语义检索版 RAG。

它的整体流程是：

用户问题 → 用 BGE 模型转成 query embedding → 到 ChromaDB 检索 top 5 文档 → 拼成 context → 构造 prompt → 调用 DeepSeek → 输出答案

也就是：

semantic retrieval + prompt + generation

它比 simple_rag_v1.py 进步的地方是：

版本 检索方式
simple_rag_v1.py 文件名关键词匹配
simple_rag_v2.py embedding 向量语义检索

retrieval(query) 做了什么？

流程是：用户问题 → 转成列表 → encode 成向量 → Chroma 查询 top 5 → 取出 documents

然后：

把检索到的文档拼成 context。

这就是 RAG 里的：召回 → 拼接上下文

8. simple_rag_v3.py：LangChain 版 RAG

这一部分是把前面的手写流程换成 LangChain。

前面是手动写：读取文件 → 切分 → embedding → 存入 Chroma → 检索 → prompt → LLM

LangChain 版把这些东西封装成组件。

加载大模型

这里还是 DeepSeek，只是通过 LangChain 的 ChatOpenAI 调用。

加载 embedding 模型

这对应之前手写版里的：SentenceTransformer(...)

指定知识库文件夹

file_dir = Path('my_knowledge')

知识库仍然是：

my_knowledge

文本切分器

这一步比 file_db.py 更进一步。

前面的 file_db.py 是：一个 txt 文件 = 一个 document

这里变成：一个 txt 文件 → 多个 chunk

并且：

每个 chunk 约 500 字，相邻 chunk 重叠 100 字。

这更符合真实 RAG 系统。

创建 Chroma 向量库

这里创建了新的持久化向量库：

./chroma_v3

创建 retriever

retriever = vector_store.as_retriever(search_kwargs={'k': 5})

意思是：

把 Chroma 向量库包装成检索器，每次检索返回前 5 个相关 chunk。

创建 prompt template

这里的 {context} 和 {question} 是两个占位符。

运行时会变成：

context = 检索到的文档片段，question = 用户问题。

创建 chain

接收用户问题 → 保留 question → 用 question 去 retriever 检索 context → 把 question 和 context 填入 prompt → 交给 llm → 把输出解析成字符串

也就是完整 RAG 链：question → retriever → context → prompt_template → llm → answer

主程序做什么？

流程是：

加载 my_knowledge 里的 txt 文件 → 切成 chunk → 加入 Chroma 向量库 → 输入问题 → 执行 RAG chain → 输出答案
