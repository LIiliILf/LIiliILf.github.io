近年AI发展梳理

从 LLM 到可靠应用

这几年也学习了很多，整理这几年的名词概念，发现有一条比较明显的主线。不断地解决 LLM 使用过程中遇到的问题，让它更好用、更可靠。

LLM、Transformer、Token、Context、Prompt Engineering、FewShot、Context Engineering、工作流、Langchain、Agent、RAG、MCP、Function Calling、Skill、Harness Engineering、多模态等等等

  • Prompt Engineering（低成本提升回答效果的手段，不需要修改模型参数）
  • 微调 Fine-tuning（在已有模型基础上，用特定数据再训练，让模型更适合某个具体任务或场景。LoRA）
  • RAG（私有知识）
  • FunctionCalling函数调用（接入外部工具、调用工具）
  • MCP模型上下文协议（如何用统一方式连接和调用外部工具）
  • Agent (Agent Loop：思考 → 行动 → 观察)

模型本体：LLM 是怎么炼成的？

  • Transformer：让模型处理序列关系和上下文依赖

  • Token & Embedding：把文本切分并转成数学表示

  • Pretraining：用海量数据训练出通用语言/知识/代码能力

  • Context Window：模型运行时一次能看到的“工作台”

起源：用海量的数据训练语言模型，后来似乎涌现了智慧，于是有了LLM大语言模型。大语言模型在预训练过程中学习了大量世界知识，在回答时不断预测下一个 Token。

发展：奠定了大语言模型的技术基础，涌现了很多 chatbot，这也是一开始人们和大语言模型交互的基本形式。

刚开始的大语言模型，能力一般般，这几年一方面是模型不断进步，另一方面是人机交互的改进。

Prompt Engineering 提示词工程

背景：同样的模型也会得到不同的回答，为了有更稳定的回答，通过设计和优化提示词，让LLM更稳定地输出。

提示词工程：通过设计和优化提示词，使大模型更准确、可控地输出，是一种可以提升模型输出效果且低成本的调优手段（不需要改变模型参数）

重要的手段和技巧：Few-shot（少样本提示）、CoT（思维链）。具体可以看 提示词工程

微调 Fine-tuning

背景：上面说的提示词工程是在不改变模型参数的情况下优化输出，但它有一定局限。上下文窗口有限，不可能把所有垂直领域知识都塞进 prompt；而且当我们希望模型长期稳定地遵循某种任务模式、输出格式、语气风格或领域规范时，仅靠提示词通常不够稳定。

这时候可以考虑微调，微调是在已有模型的基础上，用特定数据再训练，让模型更适合某个任务或场景。微调更适合改变模型的行为模式，例如让模型学会固定的输出格式、适应特定领域的表达方式、提升某类任务上的表现，或者减少对冗长提示词的依赖。

传统全参数微调需要更新大量模型参数，训练成本较高。LoRA: Low-Rank Adaptation低秩效应通过只训练少量低秩矩阵来进行微调，大幅降低了训练成本。

秩可以理解为一个矩阵真正独立的信息量有多少。低秩矩阵就是“看起来很大，但真正独立变化方向很少”的矩阵。

检索增强生成 (RAG)

大语言模型能够在预训练过程中学习大量世界知识，这些知识以参数化的形式隐含在模型中，经过微调后可以在许多下游任务中取得较好的表现。但参数知识是静态、难以更新和溯源的，模型在处理知识密集型任务时仍然可能遇到知识过时、无法给出有效来源、生成事实错误或虚拟引用的问题，也就是通常说的幻觉。(https://arxiv.org/abs/2005.11401)

RAG 的核心思路是：不要只让模型依赖参数中的“记忆”回答问题，而是在生成答案前，先从外部知识库中检索相关资料，再把检索结果作为上下文提供给模型，让模型基于外部证据生成回答。

因此，RAG 可以提升回答的时效性、可溯源性和事实一致性，尤其适合企业知识库、规章制度查询、技术文档问答、研究资料检索等知识密集型场景。但 RAG 不能完全消除幻觉。如果检索结果不相关、不完整、过时，或者模型没有正确理解检索内容，仍然可能生成错误答案。

RAG 早在 ChatGPT 大规模流行之前就已有相关研究， Facebook 在 2020 年 的研究提出，将模型知识分为两类：一类是存储在模型参数中的参数记忆（parametric memory），另一类是来自外部知识源的非参数记忆（non-parametric memory）。RAG 的思想就是把这两类知识结合起来：模型负责理解问题和组织回答，外部知识库负责提供可更新、可追溯的事实依据。

具体工作机制可以看：RAG

RAG 和微调都可以帮助模型适应预训练阶段没有覆盖的信息，但二者侧重点不同。RAG 更适合接入外部知识，尤其是私有资料；微调更适合改变模型的任务模式、输出格式和特定风格表达。RAG 通常更轻量、成本更低、落地更快，但它不改变模型参数，主要增强的是知识获取和证据支撑，并不会从根本上提升模型本身的能力。

Fuction calling

背景：前面提到的提示词工程、微调、RAG 主要是在提升模型回答质量或接入知识，但它们本身不一定让模型具备“执行动作”的能力。但在很多真实应用中，我们不只是希望模型“回答”，还希望它能够完成具体动作，比如查询数据库、调用接口、发送邮件、查询天气等。

大语言模型本身不能直接操作外部系统。它不能自己访问数据库，也不能自己调用业务接口。Function Calling 解决的就是这个问题：让模型把用户的自然语言请求，转换成结构化的函数调用；再由开发者侧的应用程序真正执行函数；最后让模型基于函数执行结果生成自然语言回答。

在这个过程中，可以分成几个角色：

User 是用户，负责提出需求。
Model 是模型，负责理解用户问题，并判断是否需要调用工具。如果需要，它会生成工具名称和调用参数。
Developer / Application 是开发者侧的应用程序或后端系统，负责接收模型返回的工具调用请求，并真正执行函数。
Tool / Function 是提前定义好的工具能力，例如查询天气、查询订单、访问数据库、调用外部 API 等。

OPENAI 的官方文档：Function calling | OpenAI API中将工具调用流程分为以下5步。

第一步，应用程序把用户问题和可用工具一起发给模型。例如，用户问“今天北京天气怎么样？”，应用程序同时告诉模型可以使用 get_weather(location) 这个工具，包括工具名称、功能说明和参数格式。

第二步，模型判断是否需要工具。如果模型认为这个问题需要实时天气数据，它不会直接编造答案，而是返回一个 tool call，例如：调用 get_weather，参数是 location = Beijing。

第三步，应用程序执行函数。模型本身不执行函数，真正执行的是开发者侧的程序。程序解析模型返回的工具名和参数，然后调用真实函数或外部 API，得到天气数据。

第四步，应用程序把工具执行结果再发回模型。这一步相当于把真实数据提供给模型，让模型基于函数结果继续生成回答。

第五步，模型根据工具结果生成最终回复。例如，模型拿到天气 API 返回的数据后，再组织成自然语言回答用户。

整个流程的简化：

    A-->>U: 返回最终回答

因此，Function Calling 的本质不是让模型自己执行函数，而是让模型负责“理解意图并生成结构化调用”，由应用程序负责“真正执行工具”。它让大模型从单纯的聊天回答，进一步扩展到调用外部工具完成任务。

MCP模型上下文协议

背景：Function Calling 解决的是模型如何生成工具调用的问题，但当 AI 应用要接入越来越多外部工具时，会出现新的问题：每接一个工具，都要写一套不同的集成逻辑。例如数据库有数据库的连接方式，文件系统有文件系统的访问方式等，这样会让 AI 应用和外部工具之间的连接变得复杂、重复且难以维护。

MCP（Model Context Protocol，模型上下文协议）解决的是“AI 应用如何标准化接入外部工具和数据源”的问题。官方文档中也将 MCP 描述为一种连接 AI 应用和外部系统的开放标准。

因此，MCP 的价值不止是让模型调用某个工具，而是让工具接入方式变得标准化。AI 工具不需要为每个工具单独设计一套连接方式，工具服务也更容易被不同 AI 工具复用，从而降低开发和维护成本。

如果说 Function Calling 让模型知道“要调用什么函数、传什么参数”，那么 MCP 进一步解决的是“这些函数和外部工具从哪里来、如何被统一接入”。前者偏模型调用机制，后者偏工具连接协议。

Agent

前面提到的提示词工程、微调、RAG、Funcion Calling 和 MCP，分别解决了回答质量、模型适配、知识接入和工具连接的问题。但它们本身还不足以让模型能够自主完成一项复杂任务。真实任务往往不是一次回答就能完成的，需要模型根据目标进行规划，调用工具，观察结果，再根据反馈调整下一步行动。

它通常由目标或指令、LLM、工具、记忆、规划能力和执行循环组成。模型不只是生成一次回答，而是在任务过程中持续进行“思考—行动—观察—调整”，从而逐步完成复杂任务。LLM Powered Autonomous Agents | Lil’Log

ReAct 是理解 Agent 的重要起点。ReAct 的核心思想是把推理和行动结合起来，让模型一边推理下一步该做什么，一边调用工具或与外部环境交互，再根据观察结果继续更新后续行动。来源于论文：[2210.03629] ReAct: Synergizing Reasoning and Acting in Language Models

但 Agent 不等于 ReActAgent。ReAct 是一种重要的基础范式，后续还发展出了更多 Agent 设计模式，例如工具使用、任务规划、反思改进、多 Agent 协作等。

AI Agent Workflow Design Patterns — An Overview | by Craig Li, Ph.D | Binome | Medium文中提到，规划型 Agent 更强调把复杂任务拆解成多个步骤，再按计划执行；反思型 Agent 更强调在执行后评估结果、发现问题并修正下一步；多 Agent 架构则强调让不同角色的 Agent 分工协作。

Function Calling 让模型知道“该调用什么工具”，MCP 让工具能够被标准化接入，而 Agent 则进一步把模型、工具、记忆和执行循环组织起来，让系统能够围绕目标连续行动。

Multi-Agent

单个 Agent 已经可以通过工具调用和执行循环完成不少任务，但它也有局限。模型的上下文窗口是有限的，当任务信息越来越多、工具越来越多、子任务越来越复杂时，单个 Agent 可能会出现上下文污染、注意力分散、工具选择错误等问题。所以想着用Multi-Agent完成某个事情，只需要返回结果给主Agent。

Anthropic 在When to use multi-agent systems (and when not to) 中总结，多 Agent 主要适合三类场景。

第一是上下文保护。按上下文边界拆分，而不是按职能阶段拆分。一个常见的 badcase 是让一个 Agent 写需求、一个 Agent 写代码、一个 Agent 写测试、一个 Agent 做审查。这样看起来像人类团队分工，但在 Agent 系统中容易导致频繁交接，大量 token 被用来解释背景、同步状态和弥补上下文丢失。更好的做法是：谁掌握完成某项工作所需的上下文，就让它把这一块负责到底。

第二是并行化。当任务可以拆成多个相对独立的方向时，可以让多个子 Agent 并行探索。例如研究任务可以拆成不同市场、不同来源、不同角度，让各个子 Agent 分别检索和总结，最后由主 Agent 汇总。

第三是专业化。当一个 Agent 需要面对太多工具、太多领域或冲突的行为要求时，可以拆成多个专门 Agent。比如 CRM Agent 只负责客户关系管理工具，Marketing Agent 只负责营销自动化工具，主 Agent 负责判断用户需求并路由到合适的子 Agent。

多 Agent 不应该默认使用。它会带来额外成本，包括更多 token 消耗、更多协调信息、更多 prompt 维护，以及更多潜在失败点。如果单 Agent 通过更好的提示词、工具设计或上下文管理就能完成任务，就没有必要引入复杂的多 Agent 架构。
